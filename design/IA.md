# Pass 管理控制台 · 信息架构与可管理面

落笔前先把「到底能管什么」铺开。下面每一项都对应 `TransCircle-Pass/schema.sql` 里真实存在的数据，不是凭空加的功能。

## 为什么当初显得像半成品（改造前的诊断）

> **这一节是动工前的诊断，不是当前状态。** 保留它是为了说明「为什么要改」。
> 下表里的每一个 ❌ / ⚠️ 都已在本次改造中解决 —— 会话、绑定、通行密钥、恢复码、
> 授权、签名密钥、安全策略现在都有完整界面与后端接口（`PATCH /v1/admin/policy` 已实现，
> 三个开关也都真正生效）。当前能力以本文后续各节的信息架构为准。

改造前的后台有 3 个一级分区：用户、客户端、审计（用户详情是其下的独立路由）。数据库里有 18 张表，下面逐张核对**当时到底能管到什么程度** —— 已按真实代码校正，不夸大：

| 表 | 承载什么 | 现有后台的实际能力 |
|---|---|---|
| `sessions` | 活跃会话（设备、IP、最后活动） | ⚠️ 只有一个「全部下线」按钮；看不到有几个、在哪台设备、什么时候 |
| `oauth_accounts` | GitHub / X 第三方绑定 | ⚠️ 详情页以 Pill **只读展示** provider 名；无绑定时间、无对端邮箱 |
| `passkeys` | 通行密钥（每把有名字、创建、最后使用） | ⚠️ 只显示**一个数量**；不能列出、不能单独吊销 |
| `mfa_totp_credentials` | 动态口令 | ⚠️ 只能连同通行密钥一起「重置 2FA」，不能单独关闭 |
| `mfa_recovery_codes` | 恢复码（已用/未用） | ❌ 完全不可见，不能作废 |
| `refresh_token_events` | 刷新令牌族、重放检测 | ❌ 不可见 —— 这是排查盗号的第一现场 |
| `oidc_payloads`(Grant) | 用户授权了哪些业务站、什么作用域 | ❌ 不可见，无法单独撤销某个站的 SSO |
| `oauth_clients` | 客户端配置 | ⚠️ **可以编辑**，但只开放 7 个字段（名称/回调/作用域/图标/主页/启停/可信第一方）；缺描述、环境、联系人、登出回跳、令牌策略、应用类型，且回调无实时校验 |
| `oauth_signing_keys` | RS256 签名密钥、轮换状态 | ❌ 无界面（只有一个 `POST /keys/rotate` 端点，前端没入口） |
| `auth_tokens` | 邮箱验证 / 改密 / 找回令牌 | ❌ 不可见，客服无法判断「验证邮件到底发出去没有」 |
| `images` | 用户上传的头像 | ❌ 无审阅入口 |
| — | 安全策略 | ❌ **当时后端根本没有这个接口**（`admin.ts` 全文搜 `policy` 零命中，尽管 `iam-main-api.md §8` 声称有）。现已实现读写两端，且三个开关都真正作用于运行时 |

所以准确的说法不是「什么都管不了」，而是：**能看的多、能改的少，且几乎全是一刀切**。用户丢了一把通行密钥，只能把他全部因素清空重来；想切断他在某一个业务站的登录，做不到。

## 信息架构

```
概览          系统状态指标（账户数、活跃会话、二次验证覆盖率、客户端、
              已授权 SSO、近期登录失败）+ 账户状态分布 + 当前签名密钥
用户          ├ 概览    资料（可改）、账户信息、管理备注（可改）
              ├ 安全    设置新密码 · 关闭动态口令 · 作废全部恢复码 · 逐把吊销通行密钥
              ├ 会话    逐个设备可见、可单独吊销
              ├ 绑定    第三方账号，只读
              ├ 授权    授权过哪些业务站、什么作用域，可逐站撤销 SSO
              ├ 审计    该用户的完整操作链
              └ 危险区  暂停 / 封禁 / 注销 / 合并 / 数据导出
客户端        ├ 设置    名称、图标、主页、联系人、描述、环境、启停  ← 均可改
              │         （Client ID 与认证方式恒不可改；应用类型仅在「迁移待确认」
              │           状态下可改正一次，确认后锁定 —— 见 api-delta.md §4.2）
              ├ 回调    回调地址增删 + 实时校验、登出回跳
              ├ 权限    作用域、可信第一方、同意屏实时预览
              ├ 凭据    密钥轮换（含 24h 重叠期）、立即吊销旧密钥
              ├ 令牌    访问/刷新令牌 TTL、轮换策略
              └ 危险区  停用 / 删除
审计          可筛选、可展开 diff、筛选态进 URL、目标显示可读名称
员工与权限     IAM tc_main 的只读投影：谁有什么权限、从哪个身份组来
安全          账户策略（可改，有保存按钮）+ 签名密钥轮换
```

**导航不带任何数量角标。** 手机端放不下，带了就得维护两套颗粒度；数量统一归概览。

**没有独立的「会话」页。** 会话总数写进概览，具体会话在对应用户的详情里管 —— 单开一页会让「先找人再看会话」变成「先看会话再猜是谁」，方向是反的。

## 四条贯穿全局的规则

**1. 一切可改，除了不该改的。** 客户端的 `client_id` 与认证方式恒不可改 —— 改了等于换一个客户端，会静默破坏已接入方，界面上明写原因。**应用类型是个例外**：存量客户端的应用类型是迁移时从认证方式猜出来的（猜不出 SPA 还是原生、也认不出既有 M2M），所以带一个「待确认」标记，允许改正一次；确认之后才锁定。不给这条纠正路径，错误的猜测就会永久固化。其余字段全部可编辑。

**2. 一张卡片一个保存按钮。** 改动攒在这张卡自己的缓冲区，不与别的卡互相牵连。点保存 → 先弹确认框列出逐字段 diff（旧值 → 新值）→ **只有含风险字段时才升级到二次验证**。低风险改动（昵称、备注、描述、联系人）确认一次就够，不然太烦。提交是原子的，要么全成要么全不成。

**3. 危险操作 = 影响面预告 + 二次验证；不可逆的还要写原因。** 不只是「确定吗」，而是明写「这会切断 3 个业务站的 SSO、影响 12 个活跃会话」。

「是否必须填原因」**按端点定，不是一刀切** —— 逐端点清单以 `api-delta.md §三` 的表格为准。分界大致是：**不可逆或影响他人账户安全**的（封禁、注销、合并、关闭动态口令、作废恢复码、吊销通行密钥、删除客户端、立即吊销旧密钥、轮换签名密钥）必须写原因；**可逆或仅影响会话**的（强制下线、暂停/恢复、撤销单站授权、停用/启用客户端、设新密码）不强制。设密码不要求原因，是因为它本身已经带着「强制下次修改 + 吊销全部会话」的强提示，再加一道输入只会让客服想办法绕过流程。

**4. 内部 ID 不进用户可见界面。** `usr_01JQ8F3M2A7` 这种东西对人没有意义也记不住，看着就是乱码。列表、详情头、审计目标一律显示可读名称。ID 只在两处保留：接入配置（`client_id` 是接入方必须填的真实值）和排障用的复制按钮。授权中间页更严格 —— 连 scope 原始 key 都不出现，每一条都是一句人话。

## 工作人员账户互不可动

**绑定了统一身份（IAM）且在 `tc_main` 下仍持有任何权限的账户 = 工作人员。工作人员的 Pass 账户不能被其他工作人员操作。**

被挡住的范围是全部写操作：改资料、改密码、关动态口令、作废恢复码、吊销通行密钥、吊销会话、撤销授权、暂停、封禁、注销、合并、导出。读取不受影响。

| 账户状态 | 判定 | 能被其他工作人员操作吗 |
|---|---|---|
| 未绑定 IAM | 普通用户 | ✅ 可以 |
| 绑定 IAM，`tc_main` 下有权限 | **工作人员** | ❌ 全部写操作拒绝 |
| 绑定 IAM，`tc_main` 下权限为空 | 已卸任，按普通用户处理 | ✅ 可以（界面标注「曾是工作人员」） |

**唯一解锁路径**：在 IAM 的 `tc_main` 里把该员工权限撤空。撤空后本页立即解锁，无需等待重新登录。

三个实现要点：

1. **判定必须实时查 IAM**（对目标账户调 M2M 权限接口），**不能读登录时的快照**。读快照会两头出错：撤权后仍被锁住改不了，或撤权前被误放行。
2. **IAM 不可达时按「仍是工作人员」拒绝**（fail-closed）—— 证明不了不是员工，就不能动。
3. **前端只是提前告知，判定与拒绝必须在后端独立做一遍**，否则 curl 可以绕过。

界面上不渲染一排灰按钮，而是直接把危险区替换成一句说明加解锁路径 —— 灰按钮只会让人反复去点。

> **代价要认**：这条规则同时挡住了「强制下线」。工作人员账户被盗时，应急路径是先去 IAM 撤权（IAM 管理员可即时操作），再回 Pass 处置。这把应急动作强制收敛到 IAM，好处是留在 IAM 的审计里，坏处是多一跳。这是刻意的取舍。

## 管理员不能做的事（刻意的）

| 不提供 | 为什么 |
|---|---|
| 操作其他工作人员的账户 | 见上节。防止员工之间互相封禁、互改密码。 |
| 解绑用户的第三方登录 | 绑定关系属于用户自己的账户所有权。管理员误解绑会直接把人锁在门外，而这个错误用户自己纠正不了。 |
| 在后台授予/撤销管理权限 | 唯一权威是 IAM 的 `tc_main`。后台开了这个口子，等于绕过 IAM 的审计与 2FA。 |
| 从客户端反查授权用户名单 | 这个面天然会越拉越大，且容易被当成用户名单导出。需要撤销授权时从用户侧操作。 |
| 对自己执行封禁 / 注销 / 重置 2FA | 管理员在 Pass 里也是普通用户，自指操作会把自己锁在系统外。前端禁用 + 后端独立拒绝。 |

## 分页：页码直达，不是「加载更多」

所有列表用**页码分页**：显示总数与当前区间（「共 26 条 · 第 21–26 条」）、可点页码直达、可选每页 10/20/50 条、筛选或排序变更自动回第 1 页、页码写进 URL。

**这带来一次对外契约变更。** 现有后端是游标分页，而游标**跳不到第 N 页** —— 它只知道下一段从哪开始。仓库里的 `Pagination` 组件注释写得很直白：「后端为游标分页、无总数，故不做页码直达」。所以管理平面的列表端点要改成 `page/pageSize` + 返回 `total`（详见 `api-delta.md §二`）。

代价是 offset 分页在数据变动时会跨页重复或漏行。管理后台以低频只读为主，可接受；补偿手段是排序默认带稳定次键（`createdAt DESC, id DESC`），避免同值行在页间抖动。**C 端接口不改，仍用游标。**

## 响应式：按容器宽度自适应，不是按屏幕宽度

用 CSS 容器查询（`@container`），因为左栏折叠后工作区可用宽度会变，**按视口断点会判断错**。

左栏折叠**按视口**（≥1280px 展开 232px，否则收成 60px 图标条，<640px 变顶部横条），
表格与详情**按工作区容器宽度**：

| 工作区可用宽度 | 表格形态 | 详情页 |
|---|---|---|
| ≥ 1040px | 完整表格，全部列 | 双列 |
| 860–1040px | 次要列隐藏 | 双列 |
| 700–860px | 再隐一档列 | 单列 |
| < 700px | **每行变卡片**，字段带标签竖排 | 单列 |

**1280 这个折叠阈值是算出来的，不是拍的。** 左栏 232→60 会让工作区骤增 172px；若折叠点落在容器断点附近，就会出现「视口变窄、表格列反而变多」的反向跳变。取 1280 时：折叠前容器 1048（>1040，全列），折叠后 1220（同样全列），两侧同档，单调。

超宽屏内容区上限 1440px 并居中，避免一行拉太长没法读。
